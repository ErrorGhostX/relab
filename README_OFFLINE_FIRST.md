## Общая концепция

Приложение **полностью автономно** и работает **только с локальной базой данных**. Сервер используется **исключительно для синхронизации** в фоновом режиме.

### Ключевые принципы:

1. **Локальность в приоритете** - все операции выполняются локально
2. **Сервер только для синхронизации** - не блокирует работу приложения
3. **Приоритет локальных данных** - локальные изменения всегда в приоритете

## Принципы работы

### 1. Локальность в приоритете
- ✅ Все операции (создание, чтение, обновление, удаление) выполняются **локально**
- ✅ UI всегда показывает данные из **локальной базы данных**
- ✅ Приложение работает **полностью автономно** без интернета

### 2. Сервер только для синхронизации
- ✅ Сервер используется **только для синхронизации** данных
- ✅ Синхронизация происходит **в фоновом режиме**
- ✅ Ошибки синхронизации **не блокируют** работу приложения

### 3. Приоритет локальных данных
- ✅ Локальные изменения **всегда имеют приоритет** над серверными
- ✅ При синхронизации серверные данные **не перезаписывают** локальные изменения
- ✅ Конфликты разрешаются в пользу локальных данных

## Архитектура компонентов

### 1. OrderRepository (Хранилище заказов)

**Назначение**: Единственная точка доступа к данным заказов

**Принципы работы**:
- Все операции работают **только с локальной БД**
- Не делает прямых запросов к серверу
- Возвращает данные из локальной БД через Flow (реактивно)

**Основные методы**:
- `getAllOrders()` - получить все заказы из локальной БД
- `createOrder()` - создать заказ локально (статус PENDING)
- `updateOrder()` - обновить заказ локально (статус PENDING)
- `deleteOrder()` - удалить заказ локально (мягкое удаление)
- `addServiceToOrder()` - добавить услугу локально
- `deleteService()` - удалить услугу локально
- `saveOrderFromServer()` - сохранить заказ с сервера (только при синхронизации)

### 2. SyncManager (Менеджер синхронизации)

**Назначение**: Синхронизация данных с сервером в фоновом режиме

**Принципы работы**:
- Работает **только в фоновом режиме**
- Не блокирует работу приложения
- Ошибки синхронизации не влияют на работу приложения

**Процесс синхронизации**:

1. **Push** (отправка локальных изменений):
   - Находит заказы со статусом PENDING
   - Отправляет их на сервер
   - Обновляет статус на SYNCED после успешной отправки
   - Обрабатывает удаленные заказы (отправляет удаление на сервер)

2. **Pull** (получение обновлений с сервера):
   - Загружает заказы с сервера
   - Сохраняет новые заказы в локальную БД
   - Обновляет существующие заказы, но **не перезаписывает** локальные изменения

### 3. UI Компоненты (Fragments)

#### OrderListFragment (Список заказов)
- Показывает заказы **только из локальной БД**
- Подписывается на Flow из Repository
- Автоматически обновляется при изменении данных в БД
- Синхронизация происходит **в фоне** и не блокирует UI

#### OrderDetailFragment (Детали заказа)
- Загружает заказ **из локальной БД**
- Показывает данные из локальной БД
- При необходимости пытается загрузить с сервера, но **не блокирует** отображение
- Добавление/удаление услуг работает локально

#### OrderFormFragment (Создание/редактирование заказа)
- Сохраняет заказ **сразу в локальную БД**
- Пытается синхронизировать с сервером в фоне
- Не ждет ответа от сервера для продолжения работы

#### ProfileFragment (Профиль пользователя)
- Показывает данные из TokenManager (локальное хранилище)
- Сохраняет изменения в TokenManager
- Синхронизирует с сервером в фоне

## Как это работает

### Создание заказа

```
Пользователь заполняет форму
    ↓
OrderFormFragment.saveOrUpdate()
    ↓
repository.createOrder() → Сохраняет СРАЗУ в локальную БД
    - Статус: PENDING
    - serverId: null
    ↓
UI показывает новый заказ СРАЗУ
    ↓
Форма закрывается СРАЗУ
    ↓
syncManager.pushChanges() → Синхронизация в ФОНОВОМ режиме
    - Отправляет заказ на сервер
    - После успешной отправки: статус → SYNCED, присваивается serverId
```

### Обновление заказа

```
Пользователь изменяет заказ
    ↓
OrderFormFragment.saveOrUpdate()
    ↓
repository.updateOrder() → Обновляет СРАЗУ в локальной БД
    - Статус: PENDING (требует синхронизации)
    - Сохраняет все изменения локально
    ↓
UI показывает обновленный заказ СРАЗУ
    ↓
Форма закрывается СРАЗУ
    ↓
syncManager.pushChanges() → Синхронизация в ФОНОВОМ режиме
```

### Удаление заказа

```
Пользователь удаляет заказ
    ↓
OrderDetailFragment.deleteOrder()
    ↓
repository.deleteOrder() → Мягкое удаление в локальной БД
    - isDeleted: true
    - Заказ исчезает из UI СРАЗУ
    ↓
Экран закрывается СРАЗУ
    ↓
syncManager.pushChanges() → Синхронизация в ФОНОВОМ режиме
    - Отправляет удаление на сервер
    - После успешного удаления: заказ полностью удаляется из БД
```

### Добавление услуги

```
Пользователь добавляет услугу
    ↓
OrderDetailFragment.addServiceToOrder()
    ↓
repository.addServiceToOrder() → Сохраняет СРАЗУ в локальную БД
    - serverId: null
    - Заказ помечается как PENDING
    ↓
UI показывает новую услугу СРАЗУ
    ↓
Синхронизация в ФОНОВОМ режиме (если есть serverId)
```

### Удаление услуги

```
Пользователь удаляет услугу
    ↓
OrderDetailFragment.deleteService()
    ↓
repository.deleteService() → Удаляет СРАЗУ из локальной БД
    - Заказ помечается как PENDING
    ↓
UI обновляется СРАЗУ
    ↓
Синхронизация в ФОНОВОМ режиме (если есть serverId)
```

## Статусы синхронизации

### PENDING
- Заказ изменен локально и ожидает синхронизации
- UI показывает заказ с локальными изменениями
- При синхронизации отправляется на сервер

### SYNCED
- Заказ синхронизирован с сервером
- Локальные данные совпадают с серверными
- При изменении статус меняется на PENDING

### ERROR
- Ошибка при синхронизации
- Заказ остается с локальными изменениями
- При следующей синхронизации повторяется попытка

## Обработка конфликтов

### Приоритет локальных данных
- Если заказ изменен локально (PENDING/ERROR), серверные данные **НЕ перезаписывают** локальные
- Локальные изменения всегда имеют приоритет
- Конфликты разрешаются в пользу локальных данных

### Пример конфликта:
1. Пользователь изменяет заказ локально → статус PENDING
2. Другой пользователь изменяет тот же заказ на сервере
3. При синхронизации:
   - Локальные изменения отправляются на сервер (перезаписывают серверные)
   - Серверные изменения **НЕ загружаются** (локальные в приоритете)

## Работа без интернета

### Все операции работают локально:
- ✅ Создание заказов
- ✅ Обновление заказов
- ✅ Удаление заказов
- ✅ Просмотр списка заказов
- ✅ Просмотр деталей заказа
- ✅ Добавление/удаление услуг
- ✅ Редактирование профиля

### Синхронизация откладывается:
- Заказы остаются со статусом PENDING
- При появлении интернета синхронизация происходит автоматически
- Пользователь может работать полностью автономно

## Преимущества

1. **Мгновенная работа** - все операции выполняются локально
2. **Работа офлайн** - приложение работает без интернета
3. **Надежность** - ошибки синхронизации не влияют на работу
4. **Приоритет локальных данных** - пользователь всегда видит свои изменения
5. **Фоновая синхронизация** - не блокирует UI
6. **Автоматическое обновление** - UI обновляется при изменении данных в БД

## Схема работы

```
┌─────────────────┐
│   UI (Fragment) │
└────────┬────────┘
         │
         │ Запрос данных
         ▼
┌─────────────────┐
│ OrderRepository │ ← Все операции локальные
└────────┬────────┘
         │
         │ Чтение/Запись
         ▼
┌─────────────────┐
│  Local Database │ ← Единственный источник данных для UI
│    (Room DB)     │
└─────────────────┘

         │
         │ Синхронизация (фон)
         ▼
┌─────────────────┐
│  SyncManager    │ ← Только синхронизация
└────────┬────────┘
         │
         │ Push/Pull
         ▼
┌─────────────────┐
│     Server      │ ← Только для синхронизации
└─────────────────┘
```
